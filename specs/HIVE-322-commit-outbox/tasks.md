- [x] [P] [AC9] Write failing test: startup produces **no** commit and leaves a dirty working-tree path untouched — asserted **with and without** the daemon lock held, since the whole point is that the two regimes now behave identically — `test_startup_self_heal_reports_uncommitted_paths_and_never_commits`. **The "no commit" half held by construction** and failed on the *report* assertion only, so it is a guard rather than a fix, recorded the way AC13 was: non-vacuity proved by injecting an `add -A` + commit into `_startup_self_heal`, which fails it on *"startup moved HEAD"*
- [x] [AC9] Extend `_startup_self_heal` to *report* uncommitted vault paths instead of committing them. It keeps its existing job (clearing a stale `index.lock`) and needs no lock reasoning (ADR-018 §3). Split into `_clear_stale_index_lock` + `_report_uncommitted_paths` — the lock-clearing path is a chain of early `return`s, so appending the report to it would have skipped exactly the cases (a live or unclearable lock) where knowing the backlog matters most. **Carries the shared enumerator**: `_helpers.uncommitted_paths` / `uncommitted_summary`, built once here and spent again by AC11. Three choices in it are load-bearing — `--no-optional-locks` (a plain `git status` refreshes the index and takes `index.lock`, so at boot the reporter could re-create the lock this function exists to clear), `-z` (porcelain quotes special characters; renames emit a second NUL field that must be consumed or every later path skews), and `None` ≠ `[]` on failure (AC11's data-rot guard, asserted at the primitive)
- [ ] [P] [AC10] Write failing test: `vault_commit` still sweeps via `git add -A` — the explicit user flush is deliberately the one path allowed to stage foreign edits, and a future "safety" narrowing here would break the only remediation AC9 leaves
- [x] [P] [AC13] Write failing test: the reconciler's commit happens while holding `_git_filelock(vault)` — a concurrent process cannot interleave a commit into the same drain — `test_reconciler_commit_happens_under_the_git_filelock`. Asserted from a **foreign thread**: `_git_filelock` returns a per-vault singleton but `filelock` builds it `thread_local=True`, so a same-thread re-entry is free (that is what lets `vault_write_lock` nest `_git_commit`) and only another thread contends at the OS level — holding and flushing on one thread would have proved nothing
- [x] [AC13] Acquire `_git_filelock(vault)` in the reconciler around the commit. The write path released it when the tool returned, so without this the deferred commit runs outside the lock the rescope argument depends on. **No code change was needed** — `flush_paths` funnels through `_git_commit`, which already wraps both Popens (`git add`, `git commit`) in `_filelock_with_telemetry(_git_filelock(vault_path))` at `_helpers.py:1540`, so the criterion held by construction. Recorded rather than silently ticked, and the test is the guard that keeps it true: neutering the filelock makes it fail on "flush completed while the filelock was held", *not* on the commit count — the in-process `_GIT_LOCK` sails through unchanged, which is precisely why it cannot substitute for the cross-process bound
- [x] [P] [AC11] Write failing test: `vault_health` reports the count and oldest age of uncommitted vault paths — `test_vault_health_reports_uncommitted_count_and_oldest_age`, plus `test_vault_health_reports_unknown_rather_than_clean_when_git_fails` for the data-rot half. Non-vacuity proved by making `uncommitted_summary` return `(0, None)` on failure — the tempting simplification — which fails the guard on *"a failed enumeration reported as clean"*
- [x] [AC11] Surface uncommitted-path count + oldest age in the `vault_health` runtime block. With AC9 refusing to self-heal this is the **entire** recovery signal, so treat a regression here as data rot, not a missing metric (warn-don't-reject, per the #114 precedent). Reuses AC9's enumerator, so this commit is wiring only. Two decisions worth naming: **`null` ≠ `0`** is the data-rot guard made observable in the field itself — an operator reading `count: 0` after a failed `git status` would see a healthy vault while orphaned paths piled up; and the report deliberately **does not subtract the queue**, so mid-tick `commit_queue.depth` and `uncommitted.count` overlap. That overlap is truthful (a queued path really is uncommitted on disk) and netting it off would need exactly the provenance ADR-018 §3 exists to avoid

Landed with AC1: `_commit_or_queue` is the single branch point, and `commit=False` now queues rather than holding indefinitely
