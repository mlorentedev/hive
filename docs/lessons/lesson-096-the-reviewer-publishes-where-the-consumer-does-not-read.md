# The reviewer publishes where the consumer does not read

**Context:** `dotf pr triage-queue` answers one question — which open PRs carry reviewer output nobody has dispositioned. It reads a per-repo registry (`harness/review-attestation.json`) naming the reviewers and the markers that identify their output. hive had no registry, so the command could not answer and exited non-zero on every run (#403). Porting one from `mlorentedev/dotfiles` looks like copying a file.
**Problem:** It is not, and the reason is invisible from the file. GitHub exposes a PR's discussion through **three separate surfaces**: issue comments, the reviews API (`reviews[]`), and inline review comments. `gh pr list --json comments` — what the queue actually calls — returns **only the first**. On this repo CodeRabbit files *proper* reviews: #401's five findings live in `reviews[]` as `**Actionable comments posted: 5**`, and `comments` held only the walkthrough. So registering the review's own text as the marker would have produced a queue that was permanently, silently empty — on a repository that was being reviewed the whole time. The dotfiles registry does not hit this because its second reviewer, PR-Agent, publishes *through* the comments API, which is exactly why its own registry documents that quirk and why the marker chosen there does not transfer.
**Solution:** Register the **walkthrough comment** — the one comment-shaped artifact CodeRabbit posts alongside every review — as the marker, verified present on both a real review (#401) and a decline (#406). Then state the limitation in the file rather than leaving it to be rediscovered: the walkthrough is *edited* on re-review and `createdAt` does not move on an edit, so a second review after a push may not re-open the queue. The queue is a floor, not a ceiling. Closing that needs a consumer that reads `reviews[]`, which is a change to the CLI and not to the registry.
**Why:** **A monitoring config is only as true as the API call underneath it, and that call is usually not in the config.** The registry names *who* reviews and *what their output looks like*; nothing in it names the surface it will be matched against, so a marker that is perfectly accurate about the reviewer can still match nothing. The tell is the direction of failure: a wrong marker here does not error, it returns "no reviewer output yet" — the same answer as a genuinely quiet PR. Same family as [[docs/lessons/lesson-094-a-verification-command-that-selects-zero-tests|lesson-094]] and [[docs/lessons/lesson-087-a-green-review-check-can-mean-did-not-review|lesson-087]]: **a check that cannot see its subject reports the subject is fine.** Two working rules. First, when porting a config between repos, verify the *observable* it keys on against live data in the destination — one `gh api repos/…/pulls/N/reviews` versus `…/issues/N/comments` would have settled this in ten seconds, and reading the source registry for an hour would not. Second, prove a matcher in **both** directions before trusting it: this one was confirmed by watching the queue correctly omit a triaged PR *and* correctly surface an untriaged one it found on its own — a real open release PR nobody had looked at, invisible until the registry existed.
