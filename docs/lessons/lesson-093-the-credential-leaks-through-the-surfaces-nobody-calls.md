# The credential leaks through the surfaces nobody calls

**Context:** AC7 of HIVE-384 asked that a planted credential appear in no repr of the settings, no `worker_status` output, no log record and no result record. It had shipped in 4.0.0 marked complete. It had **no test at all** — see [[docs/lessons/lesson-094-a-verification-command-that-selects-zero-tests|lesson-094]]. Writing that test found two live leaks.
**Problem:** Both were on paths nobody invokes deliberately. **`repr()`:** pydantic renders field *values* in a model's repr, so `repr(HiveSettings())` contained `worker_api_key='<the key>'` verbatim. Nobody calls `repr()` on a settings object on purpose — it is what a traceback, a debug log line and a failing pytest assertion print unbidden. **A relayed error body:** `_error_detail` interpolated the provider's response body into an exception message, a log line and a result record. Some providers echo the request's `Authorization` header back in an auth-failure body, so the one call most likely to produce a detail worth showing — a `401` — is also the one most likely to carry the credential in it. The first fix covered `_post_json` and left `list_models` interpolating raw `resp.text`; `worker_status` renders that, so the same leak stayed reachable through a different status code.
**Solution:** `Field(default="", repr=False)` on every credential field, and route every error body through `_error_detail`, which removes **this client's own key** by exact string replacement. Exact rather than pattern-based on purpose: it cannot over-redact, and it cannot miss a token shaped differently than the pattern expected. A general secret scrubber over arbitrary strings is a bigger thing and is not this. Both fixes are mutation-checked — removing either turns `tests/test_credential_never_emitted.py` red.
**Why:** Two lessons, and the second is the load-bearing one. **First:** a secret escapes through the surfaces you did not write. The paths a reviewer inspects are the ones that handle the credential on purpose; the leaks live in the generic machinery — object formatting, exception messages, error relaying — where the value is a field like any other and no code mentions it by name. Ask which *machinery* touches the object, not which code touches the secret. **Second:** the destination is what makes it severe. These land in a **transcript** — a durable artifact that nothing scans, that may be synced, that later sessions read, and that nothing can un-print. The commit path has a scanner; the log and the transcript have nothing. **`repr=False` closed the two measured leaks, not the class**, and saying so is part of the fix: the idiomatic answer is `SecretStr`, which changes the field's type through `ServerContext` and six call sites, and a type migration does not belong in the PR that discovered the leak. Filed as `#397` rather than left implied, because an unstated deferral is indistinguishable from not having noticed.
